How to read an entry

Every collapsed line is level 1: one sentence, no identifier, enough to decide whether to open it. Opening it gives level 2: several sentences on what the thing does, what reads it, and what you would notice in play. A nested level 3 gives the field, formula, path or gotcha a modder would quote, plus a generated In vanilla line naming each file and the values it writes. Level 3 is written to a soft cap of five sentences; where an entry runs longer, it is because the numbers or the failure mode need the room.

Nothing here is written for engine contributors, and there is no level 4.

Static files the game expects

Most assets degrade: a missing texture logs and draws a red placeholder. Four groups do not. Do not delete these while trimming a mod:

  • Fonts. Loaded by name from UI code. A missing compiled .xnb fails when that font is first used. Keep each .spritefont and its .xnb together.
  • Compiled shaders. Effects/Simple.mgfxo, MeshLighting.mgfxo, SkinnedEffect.mgfxo, Distort/BeamFX and their XNB pairs are loaded by hardcoded name; a .fx alone is not enough.
  • UI element ids. Layouts are hot-reloadable, but code finds buttons and panels by id. Renaming one removes its behaviour even though the screen still draws.
  • Content.mgcb. Build-time only: it compiles fonts, effects, videos and tutorials into the XNB/MGFXO the runtime loads. A new font or shader needs an entry there.

Everything else under Textures, Model, Audio, Flags, Cursors, LoadingScreen and Video is replaceable by relative path, and a missing file degrades that one screen or object.

Two-pass depth

Level 3 is drafted long first, then cut to about five sentences. The draft carries the number, its unit, the formula it feeds and a vanilla example; the cut keeps those and drops the rest. The In vanilla line is not prose at all: the generator reads every matching file and reports the values each one actually sets, so a claim about "typical" can be checked against the checkout rather than remembered. A tag each file sets once, such as a race's StartingScout or a hull's HullName, is quoted from one file in that file's own syntax, with the number of other files that set their own, rather than 125 identical lines. A field whose number needs arithmetic also carries an Allowed range line: the bounds the code accepts and what the formula returns at each one. A style or id is described by its readers, not only its home file: the build list, the tech gate, the UI that sorts by it and the text or name keys it selects all belong in the entry.

A card marked values only has no prose level 3 yet: it shows the files and the values they set, and says that the unit, bounds and failure symptom are not documented, rather than presenting a restated value as an explanation. Where the family notes, the worked example or the section introduction already discuss the tag, the card links there instead of repeating them; where nothing on the page does, it says so and marks that the card has no level-2 summary either. A key inside an enum-keyed map such as ShipCostModifiers is not a field at all: its card names the map, the declared type and the member names the loader accepts, and quotes the file's own comment where one exists, because a name that resolves to an enum has no field whose readers could be counted.

Coverage is measured per family: each one ends with the tags it contains that no entry above names. A tag listed there is a warning, not an instruction. GameText.yaml and Codex*.yaml are id-to-text maps and are intentionally not enumerated key by key.
