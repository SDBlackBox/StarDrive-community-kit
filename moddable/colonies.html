What colonies build and what ground units, goods, edicts and relics do.

Where the files go, what they are called, and what is required

A mod is one folder, Mods/<YourMod>/. Put the game's folder tree inside it, with no Content/ step: a building goes to Mods/<YourMod>/Buildings/Civilian/My Building.xml, a troop to Mods/<YourMod>/Troops/My Troop.xml. Every file under the family folder is read, so yours can sit in any subfolder and can be called anything; the Name inside is the id that techs, planets, events, the build list and saves use.

Required and optional. Only Name is mandatory: it is the id. Every other tag can be omitted and the field keeps its default, but the default is not always zero — Unique and Scrappable default to true and a building's Strength to 5. So copy the closest vanilla file rather than writing from a blank page, then change Name, the numbers and the icon. That is also how you add a building, troop or good: copy, rename, retune, and add the new id to whatever should unlock it.

What overrides what. Every file under the family folder is read, whatever it is called. An entry that reuses a vanilla Name replaces that entry; a new Name adds one. The file name is not the join key — Name is, and a tech's unlock list, a planet's building, a troop roster and a save all hold that string or the id it maps to. Renaming Name on an existing building therefore detaches it from the tech that unlocked it.

Critical: 19 building names are read from code

LoadBuildings matches these Name strings and stores the match in a static id. Rename one and the id stays 0; code that then asks for that template gets nothing, and the capital and space port paths throw before the colony exists.

How to test a change

  1. Keep a copy of the vanilla file. Restoring it is the fastest way to prove which change moved the result.
  2. Restart the game. These XML and YAML files are read once at startup, and a running game keeps the values it loaded.
  3. Read the load error before anything else: Failed to parse XML: <relative path> names the file the reader rejected.
  4. Start a new game for anything used at galaxy or colony creation (capital, space port, terrain, artifacts). A save keeps the buildings it already has.
  5. Look at the screen that uses it: the colony build list and a colony's building panel for buildings, the troop list for troops, the trade and freight views for goods, the governor panel for edicts, the empire summary for artifacts.
  6. Change one number at a time. Two changes in one run cannot tell you which one moved the result.

Buildings are the colony's modules: flat and per-colonist bonuses, upkeep, storage and defence. Troops fight on the surface and in boarding, goods move through the freight network, edicts are the governor's presets, and artifacts are permanent empire bonuses. A few buildings are found by name in code, so renaming one removes behaviour the XML never described.

Level 3 — how this section works

A building's Icon is a sprite family, not a path: Buildings/icon_<Icon>_48x48 and _64x64 must both exist. Maintenance is per turn and Cost is one-off; Income and PlusTaxPercentage are credits. Troop Strength is current HP and MaxStrength the cap, with level adding five percent to both attacks and range at level five. Planet edict thresholds are fractions of storage, not absolute amounts. Artifact bonuses stack across the collection and the Spiritual trait multiplies each one.

  • Namestring Building UID and display name.

    Vanilla span: 402 to 18,207 across 52 vanilla values.

    It is the short form used in the build list and tooltips, while `DescriptionIndex` is the long form. An index of zero means the field is skipped and the list falls back to the name. A wrong id shows blank rather than the XML text.

    In vanilla: Buildings/Scripted/Active Volcano.xml — <ShortDescriptionIndex>4239</ShortDescriptionIndex>; the other 51 files set their own.

  • Iconstring Icon family name.
    Buildings/icon_<Icon>_48x48 and _64x64.
    Level 3 — the detail

    A sprite family name, not a path: the colony screen looks for Buildings/icon_<Icon>_48x48 and _64x64. One missing size shows a placeholder at that zoom rather than failing the building. Reusing another building's Icon is the fastest way to add a variant without new art.

    In vanilla: Buildings/Events/The Underhive Assassins.xml — <Icon>underhive</Icon>; the other 114 files set their own.

  • ShowOnPlanetListbool Shows the building in the planet list.
    `PlanetListScreenItem` adds it to the colony's icon row when the flag is set.
    Level 3 — the detail

    The planet list is the sidebar of colony icons, and this flag decides which buildings get one. It is a display field only: hiding a building from the list does not hide it from the colony screen or the AI. `Category` still controls which build tab lists it.

    In vanilla: Buildings/Events/AI.xml — <ShowOnPlanetList>true</ShowOnPlanetList>; all 46 files set it the same way.

  • Uniquebool Allows only one of the building per planet.
    `SBProduction` refuses a second copy and logs a warning.
    Level 3 — the detail

    The check is `q.Building.Unique && P.BuildingBuilt(q.Building.BID)`, so a duplicate is dropped from the queue with a warning rather than built silently. `BuildOnlyOnce` is the broader build-order restriction. A unique building can still exist on every planet.

    In vanilla: Buildings/Civilian/Biospheres.xml — 1 entry: false; Buildings/Civilian/Terraformer.xml — 1 entry: false.

  • BuildOnlyOncebool Restricts the building to a single build order.
    `Building.IsSuitableForBlueprints` excludes it from plans, and `Empire` consults the existing buildings before ordering it.
    Level 3 — the detail

    `IsSuitableForBlueprints` returns false for a build-once building, so blueprints never place it. `Empire.cs` also checks the planet's buildings before it hands the order out. The per-planet duplicate limit is `Unique`; this flag is the stricter, empire-facing version.

    In vanilla: Buildings/Events/The Underhive Assassins.xml — <BuildOnlyOnce>true</BuildOnlyOnce>; all 6 files set it the same way.

  • Scrappablebool Whether the building can be scrapped.
    `Building.IsSuitableForBlueprints` requires it, and the defence picker only scraps buildings that have it.
    Level 3 — the detail

    `Planet_BuildDefenses` looks for the weakest military building that is also `Scrappable`, so a protected building is never removed for a new one. Blueprints also skip a non-scrappable building. The default is true, so the tag is written only to protect something.

    In vanilla: Buildings/Civilian/Capital City.xml — <Scrappable>false</Scrappable>; the other 63 files set their own.

  • CanBuildAnywherebool Lets the building ignore tile restrictions.
    `Building.cs` uses it when it places an event building and when it searches for a valid tile.
    Level 3 — the detail

    The flag appears twice in `Building.cs`: once to stop an event building forcing a random habitable tile (line 414), and once in the tile filter at line 426, where an ordinary building needs `NoBuildingOnTile`. A building with it can sit on any free tile, which is how crash sites and event structures land anywhere.

    In vanilla: Buildings/Civilian/Biospheres.xml — <CanBuildAnywhere>true</CanBuildAnywhere>; the other 52 files set their own.

  • NoRandomSpawnbool Keeps the building out of the random event pool.
    `SolarSystemBody` filters event buildings with `EventHere && !NoRandomSpawn`.
    Level 3 — the detail

    That filter decides which buildings can be placed as a random ruin on a generated tile. Setting it means the building appears only when an event or a file names it. `EventSpawnChance` is the frequency for the ones that stay in the pool.

    In vanilla: Buildings/Events/Ancient megacity.xml — <NoRandomSpawn>true</NoRandomSpawn>; all 14 files set it the same way.

  • WinsGamebool Marks the building as a victory condition.
    `Planet_ConstructionQueue` sets `HasWinBuilding` when it is true.
    Level 3 — the detail

    One building with this flag on any of an empire's planets is enough to set the win flag, so a mod can make a hidden structure the objective. The check runs when the queue finishes the building, not continuously. It is the only building field the victory code reads.

    In vanilla: Buildings/Remnant tree/Ascension Array.xml — 1 entry: true.

  • Categoryenum The palette group the building is listed under.
    The type is `BuildingCategory`, and the colony build list groups and sorts by it.
    Level 3 — the detail

    `BuildingCategory` is a fixed enum, so a value outside it becomes the default. The label does not change behaviour; it decides which tab lists the building and which filter the AI uses when it looks for a kind of building. `Technology` classifies buildings from their numbers, not from this field.

Planet edictsTier 21 file
A standing order for a colony: what it should prioritise and how much it keeps.

XML · ResourceManager.LoadPlanetEdicts

Edicts are the governor's sliders in preset form. They do not change output directly; they change what the colony does with it.

Level 3 — the detail

Thresholds are shares of storage. Priority values weight the three outputs.

Copy this: a planet edict

The whole of vanilla's PlanetEdicts/Core.xml, shortened by three fields:

<PlanetEdict>
  <Name>Core</Name>
  <Localization>120</Localization>
  <Description>1</Description>
  <PreventStarvation>true</PreventStarvation>
  <FoodPriority>0.1</FoodPriority>
  <ProductionPriority>0.45</ProductionPriority>
  <ResearchPriority>0.45</ResearchPriority>
  <FoodImportThreshold>0.2</FoodImportThreshold>
  <FoodStoreThreshold>0.3</FoodStoreThreshold>
  <FoodExportThreshold>1.0</FoodExportThreshold>
  <BuildsTroops>true</BuildsTroops>
  <BuildsDefensePlatforms>true</BuildsDefensePlatforms>
</PlanetEdict>
  • Thresholds are fractions of that resource's storage: import below 0.2, store below 0.3, export at 1.0, with 0 and 1 the empty and full ends.
