Localization and text ids

The one file that holds the game's words: how an id becomes text, how a mod's entries merge with vanilla's, and every content field that points at it.

Start here — one entry, one string

The file, a minimal entry, and the two ways to reach it 
NewGame:
 Id: 1
 ENG: "New Game"
 RUS: "Новая игра"
 SPA: "Nueva partida"
 UKR: "Нова гра"
 GER: "Neues Spiel"
 PTB: "Novo Jogo"

A mod puts its own copy at Mods/<YourMod>/GameText.yaml. There is no Content/ step: the mod folder already is the content folder, and a mod that has a Content/ inside it is rejected at startup. Only the keys you change need to be in the file, and a key you leave out keeps vanilla's text in every language.

partrequiredwhat it is
the block keyyesthe NameId, the string code passes to Localizer.Token
Idnothe integer other content files store; omitted ids are generated
ENGin practiceEnglish, the fallback every other column reads
the other sixnoa translation per language; a blank one falls back to ENG

Two addresses, one string. Other files reach it either by the number (NameIndex, DescriptionIndex, Localization fields are ints) or by the name (Localizer.Token("NewGame") in code). Both land in the same entry, so changing its text changes the button and any content that points at its number. Change the key instead and the by-name lookup stops finding it without breaking the number, which is why renaming a key is worse than editing it.

GameText.yaml is one YAML block per string: the block's key is the NameId code looks up, Id is the integer the other content files store, and ENG, RUS, SPA, UKR, GER, PTB and POL are the translations. The game loads vanilla's file, then the active mod's, merges them by NameId, and picks one column for the running language, falling back to English for each entry that has no translation. A mod ships only the keys it changes; every other string stays vanilla's.

Level 3 — how this section works

Code reaches text three ways: an int field is resolved as Localizer.Token(id), a LocalizedText field takes an int or a string, and Localizer.Token(nameId) looks a key up by name and hands back the name unchanged when it misses. A string containing braces is parsed for {id} or {NameId} tokens, and any other string is shown raw, so an id written into a plain string field displays as a number. Vanilla has 4,011 entries up to id 100,297, and 29 of them carry no Id at all, so their numbers are generated after the highest one and move when entries are added. That is why a content file should only point at an id the text file states explicitly.

How the file is loaded and merged

stepwhat happens
vanillaResourceManager.LoadLanguage(GlobalStats.Language) reads Content/GameText.yaml before fonts load, at startup and again whenever the language option changes
modif Mods/<Mod>/GameText.yaml exists it is parsed and appended to vanilla's list; a mod whose folder contains its own Content/ is rejected at startup
mergeentries are joined by NameId: a matching key replaces the text and keeps vanilla's number; any other key keeps its declared Id, or is given one after the highest id in the file
selectthe column for the running language is taken per entry, falling back to ENG; the chosen text is stored at Strings[Id - 1]
reloadswitching language re-reads both files, clears the parse cache and rebuilds the codex hooks

Two different keys that declare the same Id do not merge: the second write replaces the first in the array, so both keys show the second text and nothing is logged. Two files that declare the same key merge, and the mod's text wins.

Vanilla has 4,011 entries, 3,982 of them with an explicit Id. The GameText C# enum is generated from this file by SDGameTextToEnum.exe, and the game's own --run-localizer switch does the same merge and export; neither is needed to ship a mod.

Which ids a mod should use

Nothing in the file assigns a range to mods, so pick one and stay in it. 60,000–65,535 is the band that works in every field:

  • It sits above every general id vanilla uses today (18,285) and below the codex block at 100,000.
  • Its ceiling is 65,535 because ShipModules/*.xml stores NameIndex and DescriptionIndex as ushort. A module cannot hold 70,000, so an id above 65,535 can never be attached to one.
  • Vanilla's general text grows upward from 18,285, so the far end of 1–99,999 is the part a future update would reach last.
  • 200,000–299,999 is written down as reserved. Above 300,000 nothing is claimed, but only text reached by name or through LocalizedText can use it; no module, tech, building or artifact field can.

A clash does not break the load, which is why it ships unnoticed. Entries merge by NameId first, then each one writes its text at Strings[Id - 1], and the mod is read after vanilla, so the mod wins the write. A mod id that matches a vanilla id silently replaces that vanilla string, and every vanilla file pointing at the number then shows your text. Nothing is logged. Check before you commit: grep -n "Id: 61234" GameText.yaml.

Those are the only files that read a text id. A module, a tech and a building are therefore translatable by number, while a hull, a design, a troop, a race's name and plural, a good's <Name>, a system's name and every dialog line are raw strings that are shown exactly as written.

A module, end to end. Two numbers in the XML, two blocks in the mod's GameText, nothing else:

<!-- ShipModules/ModReactor.xml -->
<NameIndex>61000</NameIndex>
<DescriptionIndex>61001</DescriptionIndex>

# Mods/<Mod>/GameText.yaml
ModReactor:
  Id: 61000
  ENG: "Fusion Reactor"
  RUS: "Термоядерный реактор"
ModReactorDesc:
  Id: 61001
  ENG: "Adds 40 power and stores 200."

The module does not name the keys, only the numbers, so the keys can be renamed freely. Get an Id wrong and that area of the module is blank; get a key wrong and the number still resolves.

Two things follow. A name is translated only if its file has one of those fields, so renaming a UID, a hull or a design changes nothing on screen and adding it to GameText.yaml does nothing either. And the dialog files are the exception the other way: they never read an id, so translating them means a file per language rather than a column in the text file.

The choice is per entry, not per file: a Russian game shows RUS where it exists and English elsewhere, which is why a half-finished translation is still usable. A blank ENG has nothing to fall back to and shows blank in every language.

Tokens inside a string

"  {80}: {81}"            two ids, substituted where they stand
"{PowerCellName} is empty"   a NameId, looked up by name
"\{ {80} \}"              escaped braces stay literal

Only text with a { in it is parsed. Inside, {80} is an id and {PowerCellName} is a NameId; \{ and \} print a brace. A missing } logs a warning and stops the parse at that point, and an id with no entry logs an error and drops the segment. Parsed results are cached per raw string until the language is reloaded.

Dialog text: keywords, not ids

Diplomacy and encounter text never goes through GameText.yaml. Each line lives in an XML file, one folder per language, and the names are filled in at the moment the line is shown. This is the one place a string carries a placeholder that reaches back into content.

Diplomacy recognises SING, PLURAL, TARSYS, TAREMP and TECH_DEMAND, each also with one attached ., ,, ? or !. Encounters recognise SING, PLURAL, TARSYS, TAREMP, ADJ1, ADJ2 and MONEY, and strip the punctuation themselves. Neither reads braces, $ or brackets.

  • Whole word, space-delimited. The text is split on spaces and each word is looked up. SING resolves; SING, resolves; "SING", SING's, $SING and {SING} stay as written.
  • One mark only. SING... is not in the list and prints literally. Vanilla has a handful of those, which is how you can tell this is a word lookup and not a parser.
  • Case matters. sing is a word, not a keyword.
  • Translate around them. A translated line keeps the keywords verbatim; the name comes from the race file, so it arrives in whatever language that file is written in.
  • Renaming a DialogType loses the line. Code asks for Greeting, First Contact, OfferResponse_InsufficientTrust and the rest by exact string. Missing types are copied from vanilla English at load, so a renamed line is treated as new and the vanilla one reappears beside it.

A mod adds dialogue by shipping a file of the same name with only the DialogLines it changes, or a new file for a new race. The merge is by DialogType: your lines win, and every type your file lacks is copied from vanilla with a warning that lists them.

Writing a mod's file

PowerCellModule:
 Id: 61000
 ENG: "Power Cell"
 RUS: "Энергоячейка"
 UKR: "Енергоосередок"
  • Include only the keys you change or add. A key you omit keeps vanilla's text in every language.
  • Pick an id nothing else uses — 60,000–65,535 for a mod — and keep it stable once a content file points at it.
  • Leave out a language you cannot write; a blank column falls back to English rather than showing nothing.
  • Do not rename a vanilla key to retranslate it: rename it and every by-name lookup loses it, while the number still resolves to the old entry.
  • Quote every value, and escape a quote inside it. A colon or a # inside an unquoted value breaks the YAML.

Prompt for an LLM

Copy this when you need the same string in several languages 
You are writing entries for StarDrive BlackBox's Content/GameText.yaml. The file is a YAML map:
  the key is the NameId, an identifier that is never translated and is case-sensitive;
  Id is an optional unique integer; for a mod use 60,000-65,535, because a module's NameIndex is a ushort;
  ENG, RUS, SPA, UKR, GER, PTB, POL are the language columns.

Write one block per string I give you, in vanilla's style, two-space indent under the key:

<NameId>:
  Id: <unused id>
  ENG: "<text>"
  RUS: "<text>"

Rules:
- Keep every {123} and {NameId} token exactly as written, braces included; the game substitutes them.
- Keep \n, <color=Caption>...</color> and <li>...</li> markup unchanged.
- Translate only human text; never translate the NameId, the keys, or the markup.
- Leave out a language you cannot write well instead of guessing; a blank column falls back to English.
- Never reuse an Id, and never change an Id a content file already points at.
- Never put dialog or encounter text in this file: those live in DiplomacyDialogs// and Encounter Dialogs/, and the SING, PLURAL, TARSYS, TAREMP and TECH_DEMAND keywords there must stay exactly as written.
- Quote every value and escape an internal double quote as ".
Return only the YAML, and list any id you were unsure about after it.

Give the model the vanilla entries you are extending, not just your new strings: it will then copy the punctuation, capitalisation and <color> markup the game already uses. Check the ids it returns against the file before using them.

Copy this when you want to read the guide in a language the menu does not cover 
You are translating a modding guide for StarDrive BlackBox into the language I name below.

Translate the meaning, not the words. The reader should come away understanding what the English
reader understands, not matching it sentence by sentence. A literal rendering of this guide is a
worse translation than one that rephrases.

- Keep the register: short statements and imperative sentences, the way a technical document in the
target language is written. Do not switch to a formal form of address the documentation would not use.
- One term, one translation, everywhere. Keep the list as you go and reuse it. If a term of art has no
  settled translation, keep the English term and gloss it once, rather than inventing a word the reader
  will never meet in the game.
- Never translate: anything in <code>...</code> (paths, file names, field names, keys, ids,
  values, C# types), the tag names themselves, or anything inside <color=...>, <li>, {123}
  and {NameId}.
- Where a tag name stays in English, add one short line in the target language saying what it means, so
  the reader can follow the guide without knowing the English word.
- If you emit HTML, put translate="no" class="notranslate" on every element that holds an identifier,
  and keep a &nbsp; after it: a page translator drops the ordinary space and glues the words together.

The game's own text lives in seven columns, matching the seven values of its Language enum:
  ENG English, RUS Russian, SPA Spanish, UKR Ukrainian, GER German, PTB Brazilian Portuguese, POL Polish.
A language outside that list can be added to this guide, not to the game: LangToken has those seven
fields, and no eighth column exists for a mod to fill.

Return the text in the original's structure, and after it list every term you kept in English or had
to gloss.

The menu in the bar translates these pages live, using a machine engine, in the seven languages StarDrive ships columns for. This prompt is for any other language, or for a copy you keep: it tells the model to hold the identifiers still, to keep one rendering per term, and to gloss a term of art instead of guessing a word for it. Both routes start from the same English page. Machine output is readable rather than authoritative — a term of art can come back in its everyday sense — so check any command, path or value against the English page before you act on it.

How these files are laid out — the pattern and its sections

One block per string, keyed by the NameId code looks up, with Id and one line per language indented under it. The block's key is the name, not a field: the file is read as Array<LangToken> with NameId as its key name, so a renamed block is a different string.

The keys come in these sections:

  • Entry (2 keys) — The key and the number that reach this string.
  • Translations (7 keys) — One line per language, English first.

A block per string: a NameId, an optional integer Id, and a column per language. A mod ships only the keys it changes and inherits the rest.
