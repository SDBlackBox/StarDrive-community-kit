Map creation and solar systems

How a new galaxy is built: star types, orbital zones, planet types, spawned ruins and the name pools.

families: 6files: 43 tags: 85generated from: f02509bcf

Galaxy generation picks a star, walks its orbits, rolls a planet category from that zone's weights, then rolls minerals, fertility and random buildings. Hand-placed systems are separate files and are not touched by any of these tables, so a mod can mix a designed home system with generated space around it. Every table here is read at galaxy creation; none of it changes a save that already exists.

Level 3 — how this section works

WhichPlanet is an index into PlanetTypes.Types, not a name, so inserting a type in the middle re-points every system after it. SunPath is the opposite: a string id from Suns.yaml. SunZoneData weights are normalised per zone, so raising one category's weight changes the mix while the other weights keep their relative sizes. RandomStuff rolls a percentage once per planet of the matching type and caps the result with InstanceMax. The planet type's HabitableTileChance and PopPerTile decide how much of the surface can be settled before any building is placed.

Generation order: star from Suns.yaml → orbit count → per orbit, a category from SunZoneData → a type of that category from PlanetTypes → surface tiles, fertility and minerals → RandomStuff rolls → name from the NameGenerators pool. A hand-placed system in SolarSystems/ skips the first four steps but still gets its planets from PlanetTypes indices.

How these files are laid out — the pattern and its sections

Top-level key: value lines are settings of the file itself, and a key with no value opens a table. Each table holds one - PlanetType: item per entry, and the keys indented under an item are its fields.

Tables in vanilla: AtmosphereTypes (1), Types (1).

The keys come in these sections:

  • Globals (12 keys) — Meshes and scales shared by all types.
  • A planet type (23 keys) — One entry in Types.

Each type sets rendering meshes and textures, habitability, population per tile and fertility. Solar systems pick a type by its Id.

Level 3 — the detail

WhichPlanet is a PlanetType.Id, not the entry's position: the loader builds a map keyed by Id, so appending a type changes no existing reference.

Meshes and scales shared by all types.

Level 3 — the detail

NewRenderer is a work-in-progress switch; leave it false.

  • PlanetScalefloat The size of every planet in the galaxy, as a multiplier on the shared planet mesh.
    The shared mesh is 100 units across; vanilla's 10 draws each planet 1,000 units across before its own size variation, so this one number sets how large worlds look next to ships, stations and orbits.
    Level 3 — the detail

    Each planet's visible radius is the mesh's radius times this value times that planet's own size — a generated world adds a random 0.9 to 1.8 to its type's Scale, a homeworld uses the race's homeworld size trait, and a system file that sets a planet scale overrides both — so a replacement mesh of a different size changes what this number means. The radius is added to the planet's orbit distance when the system is generated, so raising this value also pushes every body outward by its own planet's radius. Reloading the file rescales what is drawn at once, but the stored radius and orbit keep their old size until the system is generated again. It leaves the gravity well alone — that follows the per-planet size, not this value — and it changes no population, fertility or mining figure. Near 0 every planet collapses to a point while its orbit stays; far above 10 the added radius dominates the orbit spacing, which is where neighbouring worlds start to overlap.

    In vanilla: PlanetTypes.yaml — 1 entry: 10.0.

  • RingsScalefloat How wide a planet's ring disc is, measured against the ring mesh rather than the planet.
    Vanilla's 3 is chosen for the shared ring mesh so the rings come out slightly wider than the planet; a replacement mesh needs its own number.
    Level 3 — the detail

    Rings are drawn with this scale applied on top of the planet's own scale, so PlanetScale moves the rings with the planet while this value only resizes the disc. The disc is tilted by the planet's ring tilt and drawn only when the body has rings; a type without rings ignores the value. Nothing else reads it: no orbit, click area or gravity well depends on the disc, so a ring that looks far too wide changes no gameplay. A value that draws the disc inside the planet hides its inner edge behind the surface.

    In vanilla: PlanetTypes.yaml — 1 entry: 3.

  • CloudsScalefloat How far the cloud layer floats above the planet surface.
    It multiplies the planet's radius: 1.015 is 1.5% wider, enough to keep the clouds off the surface without a visible gap.
    Level 3 — the detail

    Clouds are drawn only for types whose atmosphere preset supplies a cloud map, and the layer turns at two thirds of the planet's spin. The layer is the same sphere mesh as the planet, so this number is the whole gap between cloud and ground. At 1 the two surfaces coincide and flicker; below 1 the clouds vanish inside the planet. AtmosphereScale and HaloScale are measured from the planet-sized sphere, not from the clouds, so raising this value does not move the haze.

    In vanilla: PlanetTypes.yaml — 1 entry: 1.015.

  • AtmosphereScalefloat How far the blue haze shell sits outside the planet's surface.
    1.03 draws the haze 3% wider than the planet, which reads as a coloured rim at the edges rather than a thick envelope.
    Level 3 — the detail

    The haze is drawn only when the type has clouds and its atmosphere preset does not switch the sphere off with NoAtmosphere. It inverts the planet's own mesh, so it shows near the silhouette and disappears at the centre of the disc; at exactly 1 it is hidden in the surface. Its colour and strength come from the preset's glow colour, not from this scale. HaloScale is a separate shell with its own key, so widening one does not widen the other.

    In vanilla: PlanetTypes.yaml — 1 entry: 1.03.

  • HaloScalefloat How far the pale halo sits outside the planet, the faint shine on the sunlit edge.
    1.03 puts it 3% wider than the planet, the same shell size as the blue haze; it is drawn only on clouded worlds that do not switch it off.
    Level 3 — the detail

    The halo needs both a cloud map and an atmosphere preset that does not set NoHalo, so an airless world never shows it. It is fainter and tighter than the glow, and its brightness comes from the sun's direction rather than from this number. At 1 it lies on the surface and is lost; below 1 it is inside the planet and invisible, so raise it in small steps and watch the limb.

    In vanilla: PlanetTypes.yaml — 1 entry: 1.03.

  • GlowScalefloat How far the coloured glow and its fresnel rim sit outside the planet surface.
    1.005 keeps the glow almost on the surface, so it reads as light coming off the world rather than a separate ring; the colour and strength come from the atmosphere preset.
    Level 3 — the detail

    The glow is drawn only for a type whose preset sets a glow colour, and it stops being drawn once the camera is more than about 300,000 units away. It scales the glow mesh and the fresnel shell together, so the two always line up. At 1 or below the glow sinks into the planet and is hidden; raise it only as far as the preset's colour can carry without showing a gap. The glow always turns to face the camera, so this size is the only thing that decides how wide the light looks.
