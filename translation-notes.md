# Translating the guide

How the moddable guide is made readable in StarDrive's languages, what was measured
rather than assumed, and how to check a change to it. Written 2026-11-26.

## Two routes, one English page

The guide is authored once, in English, and generated by `build-moddable.py`. Nothing is
hand-edited. There are two ways a reader gets it in another language:

1. **The nav dropdown** — a Google Translate element in the header of the hub and all 8
   section pages. Live, machine output, covers the languages the game itself ships.
2. **The translation prompt** — in the localization section, a prompt that instructs an
   LLM to re-author the page in any language a reader names. Covers languages the menu
   does not, and produces a copy that can be kept.

Both start from the same English page, so a fix to the English is a fix to every
rendering.

## The dropdown offers the game's languages, not a guess

The list is read from the checkout, in two places that have to agree:

- `Ship_Game/GlobalStats.cs` — `enum Language`: English, Russian, Spanish, Ukrainian,
  German, Portuguese, Polish.
- `Ship_Game/Data/Localizer.cs` — `LangToken` fields: `ENG RUS SPA UKR GER PTB POL`.

Seven values, seven columns. English is the page's own language, so the menu carries the
other six: `de, ru, es, uk, pl, pt`. German and Russian come first in intent because
the game's own text is fullest there, but Google sorts the rendered list alphabetically,
so `includedLanguages` controls membership only.

`game/Content/{Advice,DiplomacyDialogs,Tutorials}/French` exist on disk, but there is no
`Language.French` and no `FRA` column, so French is not offered: the game could never
display it.

Do not promise seven filled columns. Measured in `GameText.yaml`: ENG 4011, PTB 3587,
RUS 3596, UKR 3321, SPA 1973, **GER 2**, POL 0 (POL exists in the enum and the struct but
is not a populated column). This is why a reader-side translator matters even for German.

## Keeping identifiers intact

A page translator is a text transformer, and this guide is mostly identifiers. Two rules
live in `build-moddable.py`:

- `protect(html)` puts `translate="no" class="notranslate"` on every `<code>`, `.nm` and
  `.ty`, and rewrites the ordinary space after each inline code span to `&nbsp;`.
- `page()` runs every page body through it, so a new section cannot forget.

Measured on `moddable/localization.html` with the widget forced to German: **179 of 179
`<code>` spans came back byte-identical**, including `ShipModule.NameIndex`,
`<NameTranslationIndex>`, `Localizer.Token` and `ushort`. The whitespace rule is not
cosmetic — without `&nbsp;` the translator glues `ushort` onto the next word, and a CSS
margin does not survive where a no-break space does.

Inverting the transform reproduces the unprotected build exactly, so protection costs no
content.

## What machine translation does badly

Measured on real page strings, roughly two thirds of headings came back identical or
near-identical to a human rendering. The misses cluster:

- **Register** — `Start here` → `Beginnen Sie hier`, formal where the doc addresses nobody.
- **Ambiguous jargon** — `string` → `Zeichenfolge` (a data type, not a text id), `bay` →
  `Bucht` (a coastline, not a storage rack).
- **Cross-sentence consistency** — `Draft` / `Entwerfen Sie`, `Start` / `Starts` for the
  same noun in two places.

That is why the page says machine output is *readable rather than authoritative* and tells
the reader to check any command, path or value against the English page.

## The translation prompt

It lives in `moddable-sections.py`, in the localization section, as a second
`<details class="note">` block beside the GameText YAML prompt. Its rules, in short:

- Translate the meaning, not the words. A literal rendering is worse than a rephrasing.
- Keep the register a native technical document would use; no invented formality.
- One term, one rendering, everywhere, with a running list; gloss a term of art once
  rather than inventing a word the reader will never meet in the game.
- Never translate anything in `<code>`, tag names, markup, `{123}`-style tokens, or the
  contents of `<color=…>`.
- Where a tag name stays English, add one short line saying what it means.
- If emitting HTML, reuse `translate="no" class="notranslate"` and `&nbsp;`.

It also states the honest limit: a language outside the seven columns can be added to the
guide, not to the game, because `LangToken` has seven fields and no eighth column exists.

## Checks after a change

```bash
cd ~/Code/kit
STARDRIVE_ROOT=/mnt/fire/StarDrive python3 build-moddable.py --audit   # exits 1 by design
```

Confirm the summary line: 45 families, 5,728 files, 1,077 described tags, and
`audit log: moddable-audit.txt — violations 472, findings 28, known 0`. A change to the
menu or the prompts must move none of those numbers.

Then confirm the wiring:

```bash
grep -c "includedLanguages:'de,ru,es,uk,pl,pt'" moddable-content.html moddable/*.html
grep -rl "includedLanguages:'de'" . --include=*.html   # must be empty
```

And confirm the dropdown in a real engine, because the options are built by Google's
script, not by us:

```bash
python3 -m http.server 8767 --directory . &
google-chrome --headless=new --disable-gpu --no-sandbox \
  --virtual-time-budget=45000 --dump-dom http://localhost:8767/moddable/localization.html \
  | grep -oE '<option value="[a-zA-Z-]*"[^>]*>[^<]*'
```

Expected: the empty `Select Language` option plus `de German`, `pl Polish`,
`pt Portuguese (Brazil)`, `ru Russian`, `es Spanish`, `uk Ukrainian`.

## Limits worth stating to a reader

- The widget needs internet. Offline it fails silently and the page stays English.
- Page text goes to Google on every load. An opt-in button would avoid that and has not
  been built.
- No native speaker has reviewed any rendering. Calling the German edition "reviewed"
  would be false.
